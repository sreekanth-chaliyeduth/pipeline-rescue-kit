Pipeline Rescue Kit

Stopping untested code from being merged, and rebuilding only what a change touches.

By Sreekanth C

The short version

The problem. Most software teams pass every code change through an automated build before it is merged into the main code. In Jenkins, a common build server, these builds often measure useful things, such as how much of the code is tested, but only report the result. A change that adds untested code or new code-quality problems can still be merged. Large projects also rebuild everything for every small change, so builds are slow.

What I built. A small shared add-on for Jenkins that turns those reports into a clear pass or block decision for every change, and a script that works out which parts of a large project a change affects, so only those parts are rebuilt.

How I tested it. On two public open-source Java projects, built on my own Jenkins. One is a large project made of 43 parts, whose own build had the problems above. The other is a small web application, where I made test changes, each designed to trip one specific check.

What I found. Every test change received the decision it should have. For a change to one service in the large project, only 3 of its 43 parts needed rebuilding. My first timing comparison overstated the speed gain; a fairer re-run showed a much smaller difference, within the normal spread between runs, so I withdrew that claim.

If you only have a minute, stop here. Each section below shows the build records behind these statements.

Why 92% and 0% at once?

The application's existing code is well tested. The few lines the untested change adds have no test at all. A check on the whole-application figure alone would let that change through; the second check exists for exactly that.

Why "already on main"?

The main code already had 1 code-quality warning before any of my changes. The check counts only warnings a change adds, so an old problem never blocks unrelated work.

Why is the warning change 100% tested?

Each test change trips one check only. Its new lines are tested, so the only thing blocking it is the one warning it adds.

Section 3

How the merge check decides

Every pull request (a proposed change waiting to be merged) runs through three checks in order. If any one fails, the change is blocked.

  1. Is the whole application still tested? The share of all code lines that the tests run, measured by JaCoCo. It must stay at or above 90%.
  2. Is this change tested? The share of the lines this pull request changed that the tests run. It must be at least 80%.
  3. Does this change add code-quality warnings? PMD, a static checker, reads the code for likely bugs and bad patterns without running it. A change may not add any new warning; existing ones are ignored.

A documentation-only change has no code lines to measure; the check records that and passes it.

Section 4

Rebuilding only what a change touches

Train-Ticket is made of 43 parts that Maven builds together. Normally every change rebuilds all of them. My script reads which files a change touched, picks the parts that contain them plus the parts connected to those, and builds only that set. When it cannot be sure, it builds everything.

Section 5

Build timings, and the claim I withdrew

I built the whole of Train-Ticket nine times on my Jenkins: three times with the original build, three with my new build, and three with my new build made to package every part, as the original does.

My first comparison showed the new build 38.9% faster. That was not a fair test. Many of Train-Ticket's own tests fail before I change anything: 220 of 626 failed or errored in my baseline builds. A separate run of the untouched project recorded 221; one login test behaves differently between runs, and I have not proven why. My new build stops at any part whose tests fail, so only 11 of the 43 parts were packaged, while the original packaged all of them. When I made the new build package every part, it was 12.6% faster at the median, and its three runs overlapped with the original's. Even then the work is not identical: the original also installs every part in a separate step. So I do not claim a speed-up.

Section 7

Trying this on a real team's pipeline

This is a tested proof of concept, not a production rollout. A team trying it would start small:

  1. Pick one repository and run the check in report-only mode, so it records decisions without blocking anything.
  2. Install the Jenkins plugins it relies on (JUnit, Coverage, Warnings NG and Git Forensics) and add the library as a trusted shared library, fixed to one release.
  3. Choose its own limits. 80% of changed lines tested is my choice for this demonstration, not a recommendation.
  4. Switch to blocking once the recorded decisions match what reviewers would have decided.

Not tested here: Bitbucket or any hosted Git server (I used a local Git server), cloud or container build agents, many builds at once, deployment, and security testing.

A project uses the check by adding one line to its Jenkins build file and one step at the end:

@Library('prk@lib-v1.1.1') _

Show the build file used for the test changes (examples/Jenkinsfile.multibranch) 
@Library('prk@lib-v1.1.1') _
pipeline {
    agent { label 'linux && java17' }
    options { timestamps(); timeout(time: 30, unit: 'MINUTES'); disableConcurrentBuilds() }
    tools { jdk 'jdk17'; maven 'maven-3.9.16' }
    stages {
        stage('Build and test') {
            steps {
                checkout scm
                script {
                    env.PRK_MAVEN_EXIT = sh(returnStatus: true, script: 'JAVA_HOME=/opt/java/jdk17 /opt/maven/bin/mvn -B -Dmaven.repo.local=/m2/repository -DtargetJdk=17 clean verify org.apache.maven.plugins:maven-pmd-plugin:3.28.0:pmd')
                }
            }
        }
        stage('prGate') { steps {
            script { if (env.BRANCH_NAME != 'main') { discoverReferenceBuild(referenceJob: 'petclinic-pr/main', requiredResult: 'SUCCESS') } }
            prGate(
                testResults: 'target/surefire-reports/*.xml',
                coverageReport: 'target/site/jacoco/jacoco.xml',
                coverageThreshold: 90.0,
                staticAnalysisReport: 'target/pmd.xml',
                enforce: env.BRANCH_NAME != 'main', modifiedLinesThreshold: env.BRANCH_NAME == 'main' ? 0.0 : 80.0, coverageScm: 'petclinic-demo',
                mavenExit: env.PRK_MAVEN_EXIT as int,
                revision: env.GIT_COMMIT,
                referenceJob: env.BRANCH_NAME == 'main' ? '' : 'petclinic-pr/main'
            )
        } }
    }
}

Section 8

Evidence and limits

For readers who want to check the work.

What I do not claim

  • No speed-up for the same amount of work.
  • Not production-ready, not proven on every kind of project, and no guaranteed build-time saving.
  • Train-Ticket's own tests do not all pass; the project already had failing tests.
  • No security scanning of any kind.
