Engineering scope

The work combines four areas: quality engineering, build optimization, Java modernization and pipeline reliability. Two open-source Java projects provide the execution evidence.

An open-source train-booking system from Fudan University researchers, built with Maven, the standard Java build tool. Its own Jenkins build had the problems in section 2. Fixed to commit 313886e, so every run builds the same code.

Case study 3

Build-cache reliability

BCE 1.2.3 · Maven 3.9.16 · Temurin 11

Question. Can a build cache be used in a quality gate without hiding tests that were failing when the cache was seeded?

Default cache

43 reactor entries restored

0 tests executed · Maven exit 0

Strict reconciled

626 tests executed

27 failures · 194 errors · Maven exit 1

The default cache produced a successful build without running tests. The documented reconciliation configuration and a strict cache restored correct failure behaviour. The strict cache held 11 of 43 reactor entries for this application.

Decision. Evaluate BCE, document the configuration dependency and do not select it for future core integration.

v1.0 implementation

Merge quality validation

Every pull request (a proposed change waiting to be merged) runs through three checks in order. If any one fails, the change is blocked.

v1.0 interactive demonstration

Three recorded pull-request scenarios and the decision the merge check made for each. Select one.

  1. Is the whole application still tested? The share of all code lines that the tests run, measured by JaCoCo. It must stay at or above 90%.
  2. Is this change tested? The share of the lines this pull request changed that the tests run. It must be at least 80%.
  3. Does this change add code-quality warnings? PMD, a static checker, reads the code for likely bugs and bad patterns without running it. A change may not add any new warning; existing ones are ignored.

A documentation-only change has no code lines to measure; the check records that and passes it.

Change-based build selection

Train-Ticket is made of 43 reactor entries that Maven builds together. Normally every change rebuilds all of them. My script reads which files a change touched, picks the reactor entries that contain them plus the entries connected to those, and builds only that set. When it cannot be sure, it builds everything.

v1.0 historical measurement

Performance measurements and methodology

I built the whole of Train-Ticket nine times on my Jenkins: three times with the original build, three with my new build, and three with my new build made to package every reactor entry, as the original does.

My first comparison showed the new build 38.9% faster. That was not a fair test. Many of Train-Ticket's own tests fail before I change anything: 220 of 626 failed or errored in my baseline builds. A separate run of the untouched project recorded 221; one login test behaves differently between runs, and I have not proven why. My new build stops at any reactor entry whose tests fail, so only 11 of the 43 reactor entries were packaged, while the original packaged all of them. When I made the new build package every reactor entry, it was 12.6% faster at the median, and its three runs overlapped with the original's. Even then the work is not identical: the original also installs every reactor entry in a separate step. So I do not claim a speed-up.

Practical adoption

How these findings transfer

Maven build selection

Start with a path-to-module map, keep a full-build fallback and verify the selected set against the dependency graph for every change class.

Jenkins quality checks

Treat report-based gates as code. Publish the evidence, keep the thresholds explicit and make failure the default when a report is missing.

Java version migrations

Compare test identities, not only totals. A build that reports success with zero tests is a configuration signal, not a migration pass.

Build caches

Keep strict and exploratory caches separate, include test policy in the cache key and verify that a seeded failure is still detected.

Test evidence

Distinguish executed, restored, skipped and omitted modules. Preserve reports per module and record the exact command and tool versions.

These are conditions for evaluating the approach in another codebase, not a claim of enterprise production readiness.

Technical reference: implementation and adoption

This is a tested proof of concept, not a production rollout. A team trying it would start small:

  1. Pick one repository and run the check in report-only mode, so it records decisions without blocking anything.
  2. Install the Jenkins plugins it relies on (JUnit, Coverage, Warnings NG and Git Forensics) and add the library as a trusted shared library, fixed to one release.
  3. Choose its own limits. 80% of changed lines tested is my choice for this demonstration, not a recommendation.
  4. Switch to blocking once the recorded decisions match what reviewers would have decided.

Not tested here: Bitbucket or any hosted Git server (I used a local Git server), cloud or container build agents, many builds at once, deployment, and security testing.

A project uses the check by adding one line to its Jenkins build file and one step at the end:

@Library('prk@lib-v1.1.1') _

Show the build file used for the test changes (examples/Jenkinsfile.multibranch) 
@Library('prk@lib-v1.1.1') _
pipeline {
    agent { label 'linux && java17' }
    options { timestamps(); timeout(time: 30, unit: 'MINUTES'); disableConcurrentBuilds() }
    tools { jdk 'jdk17'; maven 'maven-3.9.16' }
    stages {
        stage('Build and test') {
            steps {
                checkout scm
                script {
                    env.PRK_MAVEN_EXIT = sh(returnStatus: true, script: 'JAVA_HOME=/opt/java/jdk17 /opt/maven/bin/mvn -B -Dmaven.repo.local=/m2/repository -DtargetJdk=17 clean verify org.apache.maven.plugins:maven-pmd-plugin:3.28.0:pmd')
                }
            }
        }
        stage('prGate') { steps {
            script { if (env.BRANCH_NAME != 'main') { discoverReferenceBuild(referenceJob: 'petclinic-pr/main', requiredResult: 'SUCCESS') } }
            prGate(
                testResults: 'target/surefire-reports/*.xml',
                coverageReport: 'target/site/jacoco/jacoco.xml',
                coverageThreshold: 90.0,
                staticAnalysisReport: 'target/pmd.xml',
                enforce: env.BRANCH_NAME != 'main', modifiedLinesThreshold: env.BRANCH_NAME == 'main' ? 0.0 : 80.0, coverageScm: 'petclinic-demo',
                mavenExit: env.PRK_MAVEN_EXIT as int,
                revision: env.GIT_COMMIT,
                referenceJob: env.BRANCH_NAME == 'main' ? '' : 'petclinic-pr/main'
            )
        } }
    }
}

Scope and limitations

  • No speed-up for the same amount of work.
  • Not production-ready, not proven on every kind of project, and no guaranteed build-time saving.
  • Train-Ticket's own tests do not all pass; the project already had failing tests.
  • No security scanning of any kind.
